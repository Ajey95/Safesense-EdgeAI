# SafeSense final review click path

Open `http://127.0.0.1:8000/forecast?view=overview`. Use the five numbered buttons at the top of the dashboard.

1. **Problem.** Explain that a current value can be within range while a trend is heading toward a breach. The forecast uses the previous 60 one-minute samples to check six points over the next 30 minutes. Action begins at the earliest predicted crossing.
2. **BME680 & delivery.** Open Live Hardware and show the BME680 readings with the exact sensor event ID, wireless route, and board capture age. The paired Bluetooth receiver stores physical sensor events while the laptop remains on `Amrita`. Wi-Fi and Bluetooth each have a receipt card and a matching recent sensor delivery table with event ID, backend receipt time, temperature, humidity, MQ-135 raw value, and transport. Both remain visible when the latest reading changes route. Historical receipts are not a live-link claim. Click **Use ESP32 Wi-Fi for 120s** to join `SafeSense-TX-Laptop`, then let the timer restore `Amrita`, or use **Return to Amrita · Bluetooth** sooner. The transition log shows connection, return, Bluetooth reconnect, and probe outcomes. Radio association takes measurable time and can fail; the dashboard reports that outcome. The board sends capture and transmit uptime so delayed NVS records are not labelled fresh. MQ-135 remains an uncalibrated ADC value.
3. **Wi-Fi CSI.** Use Recorded replay to show known 0, 1, and 2-person recordings and the model output. Then select Live ESP32. The ESP32 now exports measured CSI packets over Wi-Fi UDP while the laptop is on its AP and over Bluetooth SPP when that link carries captured frames. A live Wi-Fi visit received packets without a COM11 reader, but a later AP association attempt failed, so check the source and freshness indicator before presenting it as live. The count can remain UNKNOWN when a complete valid window is unavailable or its signal falls outside the recorded model range. Expand packet details for signed I/Q pairs, amplitudes, RSSI, sequence, board time, queue drops, window quality, and recent windows. For a new room, enter the actual count when it changes; the collector then saves complete labelled 100-frame windows at the selected 5–60 second interval. Validate separate labelled sessions before using a room count. In PowerShell, set `$env:PYTHONPATH='src'` and run `.venv\Scripts\python.exe -m scripts.export_room_csi SESSION_ID --out data/live/room_name.npz`.
4. **Early forecast.** The selected room episode and model inputs are synthetic. The dashboard automatically opens each reviewed scenario at its demo minute: Compressor recovers, then warming rebounds **86**; Two-stage lab process **95**; Warm pallet and repeated door openings **80**; Bakery restart after cleaning **82**. Switching scenarios loads that minute automatically, and refreshing preserves the selected scenario and restores its demo minute. Reveal the simulator future in Reports to compare the forecast with the current threshold and ten-minute trend. The bakery example is the no-alert control.
5. **Alert action.** On the Forecast or Alerts page, when a scenario first produces a forecast warning, the dashboard automatically asks the backend to send a Telegram voice note with the room, channel, lead time, verification step, and room-specific action. Opening Live Hardware or CSI alone does not send a synthetic scenario alert. The scenario origin is retained in the API and Telegram caption. The same scenario and seed send at most once per UTC day, including across refreshes; an offline attempt retries while the dashboard remains open after internet returns. The configured recipient is currently the owner's account only. Telegram acceptance confirms posting, not listening.

## Real sensor alert gate

For an actual continuous sensor-to-forecast-to-contact run, collect at least 61 valid one-minute samples on the normal firmware, produce a real forecast crossing, and verify laptop receipt plus Telegram acceptance for the same event ID. For room counting, gather verified 0/1/2-person data and pass independent-session validation before deploying a room model. The synthetic forecast page, transport test, and unlabelled CSI capture are separate demonstrations until these gates pass.

## Transport receipts and database

Live Hardware now has an **ESP32 NVS → databases** card. The ESP32 sends queue depth, ordered pending event IDs, last enqueued ID, and last exact-ID ACK over the active Wi-Fi or Bluetooth route. The receiver journals each board status in its own SQLite database before sending it to the backend's `board_queue_status` table. The card shows that board observation, its laptop and backend storage times, the matching sensor delivery receipt and backend telemetry, and recent queue observations. A board report older than 45 seconds is marked stale. A `0/16` value is proof of an empty queue only at the board-reported time; it is not inferred from backend receipts. A serial monitor remains optional diagnostics, not the delivery path. `laptop_stored` and `backend_pending` refer to a separate laptop SQLite journal. Do not deliberately fill the 16-slot queue for a demo.

The **Return to Amrita · Bluetooth** control now cancels an active ESP32 Wi-Fi visit, including the connection phase. One dashboard click produced a `Manual return requested` status; a second was made after the dashboard visibly showed `ESP32 AP connected`. Both restored the `Amrita` SSID, and Bluetooth sensor receipts continued. The new 120-second visit retries transient UDP probe errors while the ESP32 AP remains connected; an earlier 45-second run sent 1,124 probes with no error. The Windows AP scan is retried up to three times and a slow association request is retried once before failure. Windows radio association and SPP reconnect still take measurable time.

As of 2026-10-21, the return button also requests an immediate COM15 receiver
reconnect. When already on Amrita it becomes **Reconnect Bluetooth**. Watch its
status line: **Bluetooth ready** appears only after a new board frame reaches
the laptop and the same event ID is stored by the backend. A wait state or
timeout means the handoff has not been verified. The timed 120-second return
requests the same recovery. A physical manual return from the connected ESP32
AP restored Amrita and verified a new Bluetooth event about 12 seconds later.
One Wi-Fi visit lost its AP link early but still restored Amrita and Bluetooth;
do not promise uninterrupted AP association on this Windows/ESP32 radio pair.

The backend database is `data/safesense.db`: `telemetry_events` stores event ID, device ID, timestamps, sensor/system/CSI metadata, and fusion result; `delivery_receipts` stores the transport hops by event ID; `incidents` and `devices` are separate tables. `data/live/direct_laptop.db`, `direct_bt.db`, and `direct_usb.db` are durable receiver journals. `data/live/room_csi.db` stores selected 100×50 CSI windows, optional operator count labels, transport source, RSSI, predictions, and quality. New accepted CSI packets are stored in `data/live/csi_packets.db` with their full 128 signed I/Q values when sent by the updated TX, the 50 selected model pairs, source, RSSI, board time, sequence, and any operator count active during capture. Historical packets retain only the selected pairs. The rolling count buffer remains in memory.

Export buttons are near the top of each relevant dashboard page: **Live Hardware** has wireless sensor deliveries, ESP32 NVS queue observations, and the SQLite CSV ZIP; **Wi-Fi CSI Count** has detailed accepted packets and user-collected windows in both replay and Live ESP32 modes. **Reports** groups all five downloads. These are stored records, separate from the synthetic forecast comparison. The ZIP packages application tables from the known local databases. Its `room_csi/windows.csv` is a readable one-row-per-window summary, `windows_frames.csv` contains the decoded 50 amplitude columns, and `windows_raw_blob.csv` preserves exact compressed SQLite bytes. The packet table similarly has a readable `packets.csv` and separate raw backup. `manifest.csv` and `README.txt` explain the views. The NVS CSV joins board-reported queue event IDs to exact-ID receiver payloads after delivery. A pending payload that is still only in ESP32 flash is not available to the laptop. The detailed CSI packet CSV records one received packet per row. Its `data` field contains all 128 raw I/Q values only for new protocol-v2 packets; historical selected-only records leave `data` blank and mark `full_128_iq_available=False`. Operator labels are present only for sessions the user labelled at collection time. Unlike PRoFENCH, untransmitted radio fields cannot be reconstructed. Historical rows remain historical; check timestamps, transport source, and synthetic flags.

The Live Hardware page selects `DIRECT_WIFI` or `DIRECT_BLUETOOTH` receipts for its current reading. The CSI page distinguishes recorded replay from live `ESP32_WIFI` and `ESP32_BLUETOOTH` packet sources. Bluetooth transports measured CSI but cannot itself generate Wi-Fi CSI; the ESP32 still needs nearby Wi-Fi radio traffic to capture. CSI `queue_drops` refers to its capture buffer, not the TX delivery NVS queue.
