# Wi-Fi CSI count demonstration

Open `http://127.0.0.1:8000/forecast?view=csi` after starting the local FastAPI
server. The **Recorded replay** tab has three fixed scenarios:

| Scenario | Fixed reference count | CSI source |
| --- | ---: | --- |
| Empty room | 0 | Held-out `csi_0.csv` windows |
| One person | 1 | Held-out `csi_1.csv` windows |
| Two people | 2 | Held-out `csi_2.csv` windows |

The scenario key selects only windows from its corresponding recorded count.
The count label is returned separately for comparison. It is **not** included
in the model feature array. A wrong prediction remains visible; for example,
the first held-out two-person window currently predicts one person.

## CSI passed to the model

Each recorded sample is a contiguous window of **100 CSI frames**, each with
**50 I/Q pairs** from pair positions 6–30 and 33–57. Each pair becomes one
amplitude, `sqrt(I² + Q²)`. From the resulting 100 × 50 amplitude matrix, the
backend computes five statistics per pair: mean, standard deviation, mean
absolute frame-to-frame difference, 10th percentile, and 90th percentile.
The trained random forest receives exactly **250 CSI-derived numbers**.

The selected scenario, reference people count, `sample_ID`, timestamps, RSSI,
file names, camera images, and radio metadata never enter that feature array.
The dashboard graph shows the mean amplitude across the 50 pairs for each of
the 100 frames; it is a summary for viewing, not an extra feature.

`ml/models/profench_count_012_blocked/replay_windows.npz` contains all 209
held-out 0/1/2 windows generated by `ml/training/train_profench_count.py`.
The model and evaluation are stored beside it. These generated artifacts are
ignored by Git and must be present locally for replay. To regenerate them,
run the training command in the training report against the supplied archive.

## Live route, with two ESP32 boards

The TX sends Wi-Fi packets through the room. The CSI RX board exports
`WISDOM_CSI` serial lines at 115200 baud. Run the local serial bridge, for
example:

```powershell
.\.venv\Scripts\python.exe scripts\csi_count_receiver.py --port COM11
```

Choose the actual RX COM port after checking the board identity. The bridge
posts only CSI serial lines to `/api/v1/csi-count/packets`. The backend decodes
the same 50 I/Q pairs, forms a 100-frame window, and runs the same 250-feature
model. No scenario count is posted to the live prediction endpoint. The backend
live status stays `UNKNOWN` until 100 contiguous fresh frames arrive, and
returns to `UNKNOWN` after three seconds without new packets. The personal
dashboard currently displays a generated fallback during this state; its
provenance and 20-second 3/2 timing are recorded in
`csi_live_preview_2026-10-14.md`.
The Live ESP32 panel shows the latest received frame's 50 CSI pair amplitudes,
packet sequence, RSSI, backend receipt time, and freshness only while the
stream is fresh. The bottom list shows the latest 50 window summaries from the
active source. Recorded replay windows never enter the live packet route.

The fixed scenario count in live mode is merely a **reference** until someone
physically sets and verifies that number of people in the room. Current live
ESP32 accuracy is unmeasured because the boards were not connected for this
software verification. The model's 85.6% score is from later windows of the
same 0/1/2 recordings; recording identity remains a confounder. Treat this
as a research demonstration, not a validated occupancy or safety sensor.

## One-board route

The `node1_sensor_tx` firmware can combine BME680/MQ-135 sampling, local
telemetry delivery, and CSI serial export on the same ESP32. In direct laptop
AP mode, connect the laptop to `SafeSense-TX-Laptop`, then send probes to its
existing UDP listener on port 3334. Use the CSI bridge on that board's COM
port:

```powershell
.\.venv\Scripts\python.exe scripts\csi_count_receiver.py --port <SENSOR-COM-PORT>
.\.venv\Scripts\python.exe scripts\csi_one_board_probe.py --port 3334
```

Sensor telemetry still needs its existing laptop receiver route. CSI export
uses the same Wi-Fi channel and a separate FreeRTOS task; it does not replace
the environmental measurements. The combined firmware must be built and
flashed, and both streams physically verified before calling this a live demo.

An alternative one-board route uses the `node2_csi_gateway` firmware:

The `node2_csi_gateway` firmware can run on a single classic ESP32 as the CSI
receiver and Wi-Fi access point. The laptop joins its `SafeSense-RX-V1` network
and sends UDP probes to `192.168.4.1:3333` with
`scripts/csi_one_board_probe.py`. The receiver measures those incoming radio
frames and exports `WISDOM_CSI` over USB serial; the serial bridge above sends
them to the dashboard. This requires temporarily replacing firmware on the
board if it currently runs the environmental node. Back up its flash first and
restore it when environmental sensing is needed again. The laptop's usual Wi-Fi
connection will disconnect while it is joined to the receiver's AP.

Run the serial bridge and UDP probe sender in separate terminals after the
receiver has been flashed and the laptop has joined its AP:

```powershell
.\.venv\Scripts\python.exe scripts\csi_count_receiver.py --port <RX-COM-PORT>
.\.venv\Scripts\python.exe scripts\csi_one_board_probe.py
```

Keep the FastAPI server on `127.0.0.1:8000`. Verify new `WISDOM_CSI` packets,
the live frame counter, and the actual 50 pair amplitudes before presenting a
live prediction. A one-board capture is genuine CSI but does not validate the
PRoFENCH-trained people-count model in this room or on this radio.
