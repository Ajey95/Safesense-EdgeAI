# SafeSense BME680 ESP32-S3 V2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver a review-ready software implementation for one BME680, two ESP32-S3 boards, LEDs, resistors, and a buzzer while preserving honest hardware and TinyML verification boundaries.

**Architecture:** Node 1 is the BME680/SoftAP/probe transmitter. Node 2 is the CSI receiver, deterministic fusion and local-output gateway with NVS-backed MQTT delivery. A laptop on the same SoftAP runs MQTT, FastAPI, SQLite, and the Streamlit review dashboard.

**Tech Stack:** ESP-IDF C/C++, portable C11 host tests, Python 3.11, FastAPI, SQLAlchemy, Streamlit, SQLite, MQTT, pytest.

**Spec:** `docs/superpowers/specs/2026-09-21-bme680-esp32s3-v2-design.md`

## Global Constraints

- Do not use Bosch BSEC, Bosch Sensor API, Arduino, Adafruit, or another runtime sensor library.
- Preserve `UNKNOWN != VACANT`, fail closed on stale inputs, and never let CSI veto critical environmental risk.
- Keep the rejected TinyML candidate disabled and label physical-device gates as unverified until hardware evidence exists.
- Add only reviewer-helpful comments and never expose internal prompts or setup instructions in the product dashboard.
- Update `PROJECT_MEMORY.md` at material milestones without secrets.

## Review Focus

- Every rubric column must point to runnable code, a test, a visible dashboard element, or an explicit hardware acceptance gate.
- Prefer deterministic portable units for host verification; keep ESP-IDF adapters thin.
- Run source scans for obsolete BME280/three-node language and internal-instruction leakage.
