# SafeSense V2: BME680 and Two ESP32-S3 Nodes

## Purpose

SafeSense V2 refactors the software around the hardware actually available: one BME680 module, two ESP32-S3 boards, current-limiting resistors, LEDs, and a buzzer. It must satisfy the six review-rubric categories without claiming evidence that requires physical hardware.

The implementation lives on `v2-bme680-esp32s3`. The `v1` branch remains unchanged.

## Hardware topology

### Node 1: sensor and CSI transmitter

Node 1 runs as a Wi-Fi SoftAP so the review does not depend on venue Wi-Fi. It owns:

- the custom BME680 I2C driver;
- temperature, humidity, pressure, and gas-resistance acquisition;
- relative gas-risk calibration and classification;
- a registration socket for Node 2;
- controlled 50 Hz UDP probe transmission to Node 2; and
- a sensor/network status LED.

The laptop and Node 2 join Node 1's SoftAP. Node 2 first sends a registration datagram to `192.168.4.1`; Node 1 records the peer address and begins transmitting probes. Each probe contains a versioned, checksum-protected snapshot of the latest environmental state so environmental context and CSI-driving traffic share one link.

### Node 2: CSI receiver and safety gateway

Node 2 owns:

- CSI callback capture from Node 1 traffic;
- I/Q amplitude conversion, invalid-first-word rejection, 48 data-carrier selection, filtering, normalization, and 100-frame windowing;
- guarded TinyML inference, defaulting to `UNKNOWN` until a model passes the release gate;
- deterministic environmental/CSI fusion;
- red, yellow, and green status LEDs plus a configurable active/passive buzzer;
- a bounded NVS telemetry queue restored at boot; and
- MQTT QoS 1 delivery to the laptop, with deletion only after an exact application ACK.

### Laptop

The laptop joins the SoftAP and runs the MQTT broker, bridge, FastAPI service, SQLite, and Streamlit dashboard. The broker address is configured on Node 2; no credential is stored in Git.

## Custom BME680 driver

The driver must not depend on Bosch BSEC, Bosch's Sensor API, Adafruit, Arduino, or another sensor library. ESP-IDF supplies only generic I2C transport.

The driver will implement:

- I2C addresses `0x76` and `0x77`;
- chip-ID verification (`0x61`);
- soft reset and calibration-register parsing;
- forced-mode configuration and bounded measurement waiting;
- temperature, humidity, and pressure compensation;
- heater resistance and duration configuration;
- gas ADC/range conversion to resistance in ohms;
- `new_data`, `gas_valid`, and `heat_stable` validation; and
- explicit bus, timeout, calibration, heater, and invalid-measurement errors.

The implementation is derived from the BME680 datasheet and independently checked against Bosch's permissively licensed BME68x reference formulas. Source provenance will be documented in the component README.

## Gas-risk policy

BME680 directly produces gas resistance, not a certified gas concentration or standalone IAQ score. V2 therefore reports:

- `gas_resistance_ohm` — valid raw compensated resistance;
- `gas_baseline_ohm` — clean-air exponential baseline built only from valid, heat-stable measurements;
- `gas_ratio` — resistance divided by baseline; and
- `gas_risk` — `NORMAL`, `WARNING`, `CRITICAL`, or `UNAVAILABLE`.

Until the warm-up count is reached, gas risk is `UNAVAILABLE`. Lower resistance indicates increased reducing-VOC influence. Default research thresholds are configurable: warning at ratio `<= 0.75`, critical at ratio `<= 0.50`. These thresholds are demonstration defaults, not certified safety limits. Invalid or unstable gas measurements never update the baseline and never become `NORMAL`.

## Versioned node protocol

The inter-node packet uses a fixed-width C structure serialized explicitly in network byte order. It includes:

- magic and protocol version;
- monotonically increasing sequence;
- sensor sample age and health flags;
- temperature, humidity, pressure, gas resistance, baseline, ratio, and risk;
- sender uptime; and
- CRC-32.

Node 2 rejects wrong magic/version, invalid enum values, bad lengths, failed CRC, duplicate/out-of-order sequences, and stale sensor snapshots. Protocol encode/decode is portable C and host tested.

## Edge processing and inference

The CSI pipeline retains the ESP32-S3-specific contract:

- the callback performs only validation, bounded copy, and non-blocking queue submission;
- `first_word_invalid` data is rejected rather than shifted;
- LLTF 20 MHz samples are interpreted as imaginary then real;
- the 48 non-pilot data carriers are retained in physical payload order;
- amplitudes are filtered and accumulated into `100 × 48` windows; and
- normalization parameters come only from training data.

The existing fully INT8 runtime remains fail-closed. It can be enabled only with a candidate that passes the release verifier. The current rejected public-data model is not embedded or represented as working.

## Fusion and local outputs

Fusion preserves these invariants:

- critical environmental risk always produces `INCIDENT`, regardless of CSI;
- warning environmental risk produces `WARNING`;
- unavailable/stale environmental input produces `DEGRADED`;
- stale, low-confidence, or unknown CSI can never mean `VACANT`; and
- failure never silently becomes a safe state.

Output mapping:

| State | Green LED | Yellow LED | Red LED | Buzzer |
|---|---:|---:|---:|---:|
| NORMAL | on | off | off | off |
| WARNING | off | on | off | periodic short pulse |
| INCIDENT | off | off | on | repeating urgent pattern |
| DEGRADED | off | slow blink | off | off |

Pin assignments, active levels, and active/passive buzzer mode are configured through `menuconfig`.

## MQTT and persistence

Node 2 stores state transitions and incidents in NVS before publish. A queue record is removed only after the backend responds with JSON containing the exact `event_id` and `status: ACCEPTED`. MQTT disconnects, broker rejection, malformed ACKs, duplicates, and reboot do not lose the record.

The JSON contract includes BME680 readings, gas calibration state, CSI link/window/inference state, output state, NVS queue state, and ESP32-S3 node health. The backend accepts server timestamps when node wall-clock time is unavailable.

## Dashboard and rubric alignment

The dashboard remains product-facing and contains no setup instructions or internal prompts. It shows:

- Environment: temperature, humidity, pressure, gas resistance, baseline/ratio, gas status, environmental risk;
- Wi-Fi CSI: TX/RX states, RSSI, packet rate, quality, window status;
- Human Context: activity and confidence;
- System: MQTT, local storage, Node 1, Node 2, LEDs/buzzer, queue depth;
- Recent Events; and
- active incident acknowledgement.

Review documentation maps evidence to all rubric columns: custom library, persistence, edge preprocessing/inference plan, communication reliability, dashboard, and individual presentation/Q&A.

## Failure handling

- BME680 missing/wrong ID: Node 1 reports unavailable, does not fabricate readings, and visibly signals failure.
- Heater unstable or gas invalid: temperature/humidity/pressure may remain available, but gas risk is unavailable.
- Node 2 missing: Node 1 waits for registration and does not send to an invented address.
- CSI queue overflow: callback increments a drop counter; processing continues without blocking Wi-Fi.
- Sensor packet invalid/stale: Node 2 enters degraded environmental state.
- MQTT/laptop unavailable: events remain in NVS until capacity; queue-full is visible and new records fail explicitly.
- Reboot: Node 2 restores NVS metadata and the head event before reconnecting.

## Verification boundary

Host tests must pass for the driver, gas policy, protocol, CSI, fusion, outputs, API, and dashboard. ESP-IDF builds must target `esp32s3` when the toolchain is available. Physical I2C readings, heater behavior, CSI capture, buzzer/LED polarity, reboot persistence, MQTT delivery, and on-device memory/latency remain hardware acceptance gates until observed on the two boards.
