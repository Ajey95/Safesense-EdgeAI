# SafeSense Forecast Lab — synthetic 30-minute early-warning demonstration

## What this demonstrates

The dashboard selects an **unseen synthetic scenario family** and reveals its one-minute BME680-like temperature, humidity, pressure, gas-resistance and MQ-135 raw-ADC history over time. A compact model takes the last 60 minutes plus room type and predicts all five signals at +5, +10, +15, +20, +25 and +30 minutes. Configured **demo ranges** convert those predictions into an early notification. The future generated by the simulator remains hidden from the model and is shown separately only when the viewer selects **Reveal hidden simulator future**. The forecast card's large value is the +30-minute reading; its risk time is the first out-of-range five-minute forecast point. The reveal compares that with the simulator's one-minute readings, so different times are a measurable timing error or a sampling difference. A +0-minute simulator result means the current reading was already outside range.

The existing physical V1 path already has TX ESP32 → Wi-Fi HTTP → RX ESP32 NVS → exact event-ID ACK → laptop bridge → backend. This extension builds the same forecast network into the TX firmware and adds a Bluetooth Classic SPP alert to a paired nearby laptop when the current event lacks an RX ACK. The laptop app journals the exact ID, sends an `ACK|ID` receipt, and attempts local speech. The demo fault toggle skips the TX HTTP attempt; it does **not** cut the Wi-Fi radio or prove RF failure recovery. RX storage, Bluetooth laptop storage, speech playback and backend storage are different claims.

## Curated scenario families

Each family has randomized onset, amplitude, response speed, baseline, sensor noise and weather drift. The simulator creates coupled responses, including humidity effects on gas-resistance and raw MQ values, and temporary recoveries. It does not assign chemical identities or ppm. A current sample alone does not encode the later ramp or rebound; the model uses the trajectory. The names are narrative contexts, not observed activity labels.

| Room | Train families | Held-out families shown in dashboard |
|---|---|---|
| Cold storage | Defrost fails to settle; loading door ajar | Compressor recovery then warming rebound; warm pallet plus repeated doors |
| Laboratory | Cleanup vapor build-up; weak extraction | Two-stage process; ventilation flush then accumulation |
| Classroom | Crowding with reduced air exchange; cleaning after class | After-hours cleaning with falling temperature |
| Bakery | Long oven shift; steam cleaning overlap | Restart after cleaning; cooling bottleneck |
| Server room | Cooling capacity loss; battery-service disturbance | Airflow recirculation with a short cooling dip |

This is **10 training families and 8 held-out families**, 60 training episodes per family and 20 held-out episodes per family. The [compressed dataset](../data/forecast_synthetic_v1.csv.gz) has one row per synthetic minute. The [manifest](../ml/forecast_release/synthetic_v1/dataset_manifest.json) records family membership and demo ranges. All outputs can be regenerated from `forecast_scenarios.py` with fixed seeds. The dataset generator is the canonical source; the CSV is an inspectable export.

The same project-generated export is publicly hosted as [SafeSense Synthetic Environmental Forecasting v1](https://huggingface.co/datasets/Ajeya95/safesense-synthetic-environmental-forecast-v1), with separate Parquet train/test splits, the original CSV, the generator and a provenance card. Hugging Face is the hosting and download location, not the source of independent measurements. The current trainer still generates episodes locally from the same seeded simulator; it does not download training rows from the Hub.

## Model and fair comparison

The model is a two-hidden-layer ReLU network (70 inputs → 48 → 24 → 30 outputs). Its feature vector consists of 13 past sensor snapshots at five-minute spacing plus a five-way room code. Outputs are future changes from the current reading. Training is offline; weights and normalization are exported as C arrays, and the TX ESP32 runs plain float inference without a cloud model call. The Python dashboard and C inference outputs have a host parity test. Training uses full episodes; all eight test families are excluded from fitting. No scenario key, hidden simulator driver, future value or risk label enters the feature vector.

The two useful simple baselines are **persistence** (future equals now) and **recent trend** (project the past ten-minute change). The rule that decides when to notify is intentionally separate: each method's forecast is checked against the same room-specific demo ranges.

On 160 held-out episodes with **one decision per episode at minute 75**, the saved run records:

| Method | Future range-breach precision | Recall | TP / FP / FN / TN |
|---|---:|---:|---|
| TinyML forecast | 0.750 | 0.789 | 15 / 5 / 4 / 136 |
| Recent trend | 0.800 | 0.632 | 12 / 3 / 7 / 138 |

There are only 19 positive episodes at that fixed decision point, so this difference is small and simulator-specific. Across four correlated decision windows per held-out episode, TinyML recall is 0.821 and trend recall 0.637; those 640 windows must **not** be described as 640 independent incidents. Full values and 30-minute channel errors are in [metrics.json](../ml/forecast_release/synthetic_v1/metrics.json). The model has not been validated on real rooms, real gas incidents, sensor drift, or a real 30-minute hazard. The trainer currently reaches its iteration limit before its optimization warning clears; the saved weights are evaluated, but no convergence claim is made.

## Run the demonstration

```powershell
pip install -e ".[dev,demo]"
python ml/training/train_synthetic_forecast.py
python scripts/export_forecast_dataset.py
uvicorn safesense.main:app --host 127.0.0.1 --port 8000
```

Open **http://127.0.0.1:8000/forecast** for the reference-matched dashboard. The default cold-storage episode starts at minute 82, where the current reading is inside its demo range and the forecast predicts a later crossing. Use **Run Simulation**, change room/scenario, inspect the chart, reveal the simulator's future to compare, and toggle the injected Wi-Fi send failure. The backend's `/api/v1/forecast/scenarios` and `/api/v1/forecast/episode` endpoints supply the displayed synthetic data. The older Streamlit Forecast Lab remains available through `streamlit run dashboard/app.py`, but the dedicated FastAPI page is the primary presentation. Without hardware replay, all route receipts on either page are explicitly simulated.

The five room themes keep the same card layout for comparison but change the header/sidebar palette, room art, scenario icon, tagline and chart accent. When a non-temperature channel triggers the forecast alert, the chart selects that channel and shows the relevant upper or lower demo bound. The [visual check](forecast_frontend_fidelity.md) records reference alignment and the copy changed to avoid unsupported delivery or sensor claims.

The sidebar opens distinct URL-addressable views for Overview, Scenario Forecast, Live Hardware, Sensors, Sites, Alerts, Reports, Integrations and Settings. These are separate content views, not same-page anchor jumps. [Live Hardware](live_hardware_integration.md) shows only RX-bridge-tagged telemetry and nearby laptop transport receipts, with stale data labeled; it is separate from the synthetic episode. Sites selects held-out scenarios; Reports compares the model with a ten-minute trend baseline and only computes an error after the simulator future is revealed; Integrations controls the synthetic route fault; Settings controls seed, minute and reveal state. Browser back/forward preserves view navigation.

The alert policy checks **temperature, humidity and BME680 gas resistance** against room-specific demo ranges at the six forecast horizons. The earliest crossing creates the displayed alert. Pressure and MQ-135 raw ADC remain model inputs and predicted outputs but have no alert bound in this prototype. The MQ raw value has no calibrated ppm meaning. The Alerts and Sensors views show this channel-by-channel, including the current reading, +30-minute forecast and configured range. In the default cold-storage episode temperature triggers; some laboratory/classroom episodes trigger on gas resistance.

For a physical route demonstration, build the TX firmware with `CONFIG_SAFESENSE_TX_SCENARIO_SERIAL_DEMO=y`, flash the TX board, pair the laptop with `SafeSense-TX-Alert`, and locate the Windows Bluetooth outgoing COM port. Run the laptop receiver on that port:

```powershell
python scripts/bt_alert_receiver.py --port COM16
```

In the dashboard open **View Alert Details → Connected TX hardware replay**, enter the TX USB COM port (the previous board appeared as COM11; check its current port), and send the 61-minute history. With the failure toggle off, the TX attempts its normal HTTP TX→RX route and reports RX's exact-ID ACK. With it on, it skips that HTTP send and sends a forecast alert over Bluetooth SPP when the model predicts a range crossing. The separate Bluetooth COM receiver must be running for a stored receipt and local voice attempt. The dashboard displays actual hardware route states only after the TX serial result is received. The injected sample is marked `simulated` in TX JSON and uses a synthetic device ID. The endpoint refuses an unknown scenario or invalid COM-port format and reports an unavailable board as an error, not a simulated receipt.

The replacement MQ-135 has been reported working by the user; this is a different module from the older board whose ADC was repeatedly zero. Its current pin voltage, raw ADC range and calibration are still separate physical evidence. Raw ADC is not ppm or a selective gas alarm. Real-sensor inference waits for 61 valid one-minute observations and a nonzero MQ signal. All forecast alerts from this model remain an unvalidated demonstration; direct real-world emergency dispatch or automatic actuators are outside this build.

## Research and incident context

- A [BME680 indoor air-quality forecasting study](https://www.mdpi.com/2073-4433/15/12/1529) illustrates time-series forecasting with a BME680, while [TI's embedded indoor-temperature forecasting example](https://github.com/TexasInstruments/tinyml-modelzoo/blob/main/examples/hvac_indoor_temp_forecast/readme.md) illustrates compact edge inference. Neither validates this five-channel SafeSense model.
- The [U.S. Chemical Safety Board's Didion report](https://www.csb.gov/didion-milling-company-explosion-and-fire-/) concerns combustible dust; BME680 and MQ-135 cannot measure dust explosion risk. The [T2 runaway-reaction report](https://www.govinfo.gov/app/details/GOVPUB-Y3_C42_2-PURL-gpo49796) concerns process conditions outside these room sensors. They motivate the value of early warning but are **not** scenarios this system could have prevented.
- [OSHA's 151 Foods record](https://www.osha.gov/ords/imis/establishment.inspection_detail?id=1482111.015) illustrates bakery heat risk. The [CSB Cuisine Solutions ammonia report](https://www.csb.gov/assets/1/20/cuisine_solutions_investigation_report_final_for_pdf1.pdf?17269=) illustrates a refrigerant release; this sensor pair does not identify or quantify ammonia. The bakery and cold-storage themes are only synthetic environmental narratives, not accident reconstructions.
- [Espressif documents SPP servers and virtual serial links](https://docs.espressif.com/projects/esp-idf/en/stable/esp32/api-reference/bluetooth/esp_spp.html). Its [Wi-Fi/Bluetooth coexistence guidance](https://docs.espressif.com/projects/esp-idf/en/stable/esp32/api-guides/coexist.html) matters because both share the classic ESP32 radio, so Bluetooth is not a guaranteed rescue from all interference.
